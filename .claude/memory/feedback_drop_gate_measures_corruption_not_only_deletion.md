**da#424 (#474), 2026-07-21 — three review rounds, one blind metric.** The truncate-and-re-gate recovery (recover a real leading narrator from a matn tail instead of dropping the whole span) passed with a full **bidirectional, unweighted** drop-gate A/B showing **NEWLY-DELETED = 0** — the exact instrument [[feedback_drop_gate_bidirectional_ab]] prescribes after PR #423. It still shipped two defects, each caught only by an Arabic-reading reviewer (Oyunbileg / Nikolaos) constructing adversarial isnad shapes:

1. **Severing** — the ف-narrative boundary (`فذهب` "so he went") treated any ف-initial ≥4-char token as a verb, corroborated by *any* matn signal anywhere later in the span. So `عبد الله بن فراس بن مالك القرشي في المدينه` — a real narrator whose ism is `فراس` (Firās) — was cut at `فراس` into the dangling fragment `عبد الله بن`.
2. **Nisba clipping** — corroboration accepted a bare **preposition** (`في`). A preposition attaches to a noun as readily as a verb, so a plain ف-initial **nisba** (`فارسي`/`فلسطيني`/`فرغاني`) followed by `… في المدينه` was clipped: `عبد الله بن عمر فلسطيني …` → `عبد الله بن عمر`, dropping the very nisba that distinguishes two otherwise-identical nasab leads.

**Why the A/B could not see it — a DIFFERENT axis than [[feedback_drop_gate_bidirectional_ab]].** That note's blind spot is the *deletion* axis measured *weighted* (mc=0 rows erased). This is one axis further out: the A/B was already unweighted and bidirectional, and its deletion axis was genuinely clean — the narrator was **not deleted**. The harm is that the row's NAME was corrupted to a *different, still-valid-looking* name. `clean("… بن فراس …")` returns `"عبد الله بن"` — a non-empty string, so `NEWLY-DELETED` counts zero. The damage lands downstream: a corrupted/clipped name **collapses onto a different canonical id** (a fragment merges with a stranger; a de-nisba'd lead merges two distinct people). It is a **wrong-MERGE**, and a drop-set diff — which only asks "did this row survive?" — is structurally incapable of flagging a survivor whose *value changed*.

**How to apply:**
- A drop/scrub/recover-gate A/B must measure the **CORRUPTION axis, not only the deletion axis**: diff `clean_old(row) != clean_new(row)` over the full corpus and read the `name → different name` set by hand, not just `name → None`. A recovery/truncation gate's worst failure is a survivor with a **wrong** value; "0 deleted" is necessary, not sufficient. Sibling of [[feedback_silent_zero_is_not_a_measurement]] — the number you watched (deletions) is not the number that would have told you (corruptions).
- For a name-truncation/recovery rule, the required adversarial coverage is **ف-initial ISM shapes** (`فراس`/`فديك`/`فوزي`/`فتحي` after `بن`/`ابو`) **and ف-initial NISBA shapes** (`فارسي`/`فلسطيني`/`فرغاني` before a bare preposition) — the two families this rule mis-cut. A battery of *deletion* counterexamples (real names carrying Prophet references, per #423) does not reach them; this is a premise error on a *different* feature (any ف-initial token looks like a ف-verb), so the battery must be rebuilt for the corruption shape.
- The safe fix shape here mirrors #423's precision philosophy: a ف-token immediately after a kunya/nasab connector is that name's ism (never a verb), and corroboration must be **local** (before any intervening nasab connector) **and** a genuine **narration marker** (Prophet ref / ask-verb / `_MATN_OPENERS` / `_MATN_DENSITY`) — never a bare preposition. See `_is_fa_narrative_boundary` / `_fa_narrative_corroborated` in `src/parse/name_quality.py`.
- Reinforces the #423 rule: an Arabic name rule needs an Arabic-reading reviewer constructing corpus-shaped adversarial names — the corruption here was invisible in the metric and only visible to someone reading the Arabic and building the fragment/nisba shapes on purpose.
